Database normalization is the process of organizing data in a relational database to reduce duplication and stop errors. It breaks big tables into smaller, linked tables using rules called normal forms.

Why We Normalize Data
Stop data copies.
Keep data correct and safe.
Make updates fast and easy.
Stop bugs when adding or deleting rows

The Main Normal Forms
First Normal Form (1NF): Make every cell hold only one single value, and give the table a primary key.Second Normal Form (2NF): Must be in 1NF. Remove parts of data that do not depend on the whole primary key.
Third Normal Form (3NF): Must be in 2NF. Remove columns that depend on other non-key columns instead of the primary key.

A foreign key is a column or group of columns in one table that links to the primary key of another table. It builds a parent-child relationship between data, makes sure records match up correctly, and stops invalid data or broken links from being saved.Key ConceptsParent Table: The main table that holds the original primary key.Child Table: The secondary table that holds the foreign key pointing back to the parent.Referential Integrity: The rule that stops you from adding a child row with a missing parent or deleting a parent row while child rows still depend on it.Main BenefitsData Quality: Stops orphaned records where a child item points to a thing that does not exist.Easy Linking: Makes it simple to join tables together to pull related information.Simple Code ExampleYou can learn more about syntax details on W3Schools.sqlCREATE TABLE Customers (
    CustomerID INT PRIMARY KEY,
    Name VARCHAR(50)
);

CREATE TABLE Orders (
    OrderID INT PRIMARY KEY,
    OrderDate DATE,
    CustomerID INT,
    FOREIGN KEY (CustomerID) REFERENCES Customers(CustomerID)
);

A many-to-many join table (also known as a junction, bridge, or associative table) is a structural table used in relational databases to link two other tables that have a many-to-many relationship. Relational databases like PostgreSQL, MySQL, and SQL Server cannot directly link two tables this way using a single foreign key; they require this third table to break the complex relationship down into two simple one-to-many relationships.Why Join Tables are EssentialAvoids Data Duplication: You do not have to repeat entity details multiple times just to show a new connection.Avoids Unnormalized Data: It eliminates the bad practice of storing comma-separated lists of IDs inside a single text column.Allows Meta-Data Storage: It serves as a perfect place to store information about the relationship itself (e.g., the date a user liked a post).Core Structure of a Join TableA classic example is a system where Students can enroll in multiple Courses, and each Course contains multiple Students.[ Students ] 1 ------ * [ Enrolled_Courses ] * ------ 1 [ Courses ]
1. The Main TablessqlCREATE TABLE Students (
    StudentID INT PRIMARY KEY,
    StudentName VARCHAR(100)
);

CREATE TABLE Courses (
    CourseID INT PRIMARY KEY,
    CourseTitle VARCHAR(100)
);
Use code with caution.2. The Join TableThe join table maps connections by holding the primary keys of both main tables as foreign keys.sqlCREATE TABLE Enrolled_Courses (
    StudentID INT,
    CourseID INT,
    EnrollmentDate DATE DEFAULT CURRENT_DATE, -- Optional relationship attribute
    PRIMARY KEY (StudentID, CourseID),        -- Composite Primary Key prevents duplicates
    FOREIGN KEY (StudentID) REFERENCES Students(StudentID) ON DELETE CASCADE,
    FOREIGN KEY (CourseID) REFERENCES Courses(CourseID) ON DELETE CASCADE
);
Use code with caution.How to Query a Join TableTo pull data across a many-to-many relationship, you must execute a double JOIN statement. You start at one entity table, join into the bridge table, and then join out into the destination entity table.sqlSELECT 
    s.StudentName, 
    c.CourseTitle,
    e.EnrollmentDate
FROM Students s
JOIN Enrolled_Courses e ON s.StudentID = e.StudentID
JOIN Courses c ON e.CourseID = c.CourseID;
Use code with caution.Best Practices for Designing Join Tables
Use Composite Primary Keys: Set the combination of both foreign keys as the unique PRIMARY KEY to block accidental duplicate rows.
Index the Foreign Keys: Ensure both foreign key columns are indexed to maintain fast query speeds as your data grows.
Enforce Cascade Deletes: Use ON DELETE CASCADE constraints so that if a student or course is deleted, the corresponding connection rows are cleaned up automatically.

    Path(__file__).parent.parent

from Task1_Models import db, Product


# Flask application
app = Flask(__name__)

# Task 1 ke same database ko use karna
database_path = task1_folder / "instance" / "inventory.db"

app.config["SQLALCHEMY_DATABASE_URI"] = (
    f"sqlite:///{database_path}"
)

app.config["SQLALCHEMY_TRACK_MODIFICATIONS"] = False

db.init_app(app)


with app.app_context():

    # ==========================================
    # 1. RAW SQL - SELECT ALL PRODUCTS
    # ==========================================

    print("\n========== RAW SQL ==========")

    raw_sql = text("SELECT * FROM products")

    result = db.session.execute(raw_sql)

    for row in result:
        print(row)


    # ==========================================
    # 2. ORM - SELECT ALL PRODUCTS
    # ==========================================

    print("\n========== ORM ==========")

    products = db.session.execute(
        select(Product)
    ).scalars().all()

    for product in products:
        print(
            product.product_id,
            product.product_name,
            product.current_stock
        )


    # ==========================================
    # 3. ORM QUERY
    # ==========================================

    print("\n========== ORM FILTER ==========")

    statement = select(Product).where(
        Product.product_name == "Laptop"
    )

    products = db.session.execute(
        statement
    ).scalars().all()

    for product in products:
        print(
            product.product_id,
            product.product_name,
            product.current_stock
        )


    # ==========================================
    # 4. GENERATED SQL FROM ORM
    # ==========================================

    print("\n========== GENERATED SQL ==========")

    print(
        statement.compile(
            compile_kwargs={"literal_binds": True}
        )
    )


    # ==========================================
    # 5. ORM INSERT
    # ==========================================

    print("\n========== ORM INSERT ==========")

    new_product = Product(
        product_name="Keyboard",
        current_stock=25
    )

    db.session.add(new_product)
    db.session.commit()

    print("Product inserted using ORM.")


    # ==========================================
    # 6. RAW SQL INSERT
    # ==========================================

    print("\n========== RAW SQL INSERT ==========")

    db.session.execute(
        text("""
            INSERT INTO products
            (product_name, current_stock)
            VALUES (:name, :stock)
        """),
        {
            "name": "Mouse",
            "stock": 50
        }
    )

    db.session.commit()

    print("Product inserted using Raw SQL.")


    # ==========================================
    # 7. SHOW ALL PRODUCTS AGAIN
    # ==========================================

    print("\n========== FINAL PRODUCTS ==========")

    products = db.session.execute(
        select(Product)
    ).scalars().all()

    for product in products:
        print(
            f"ID: {product.product_id} | "
            f"Name: {product.product_name} | "
            f"Stock: {product.current_stock}"
        )

TASK 3 — UNDERSTANDING

Topic: DATABASE MIGRATIONS WITH ALEMBIC & DJANGO

The purpose of this task is to understand database migrations—how changes in your models are converted into migration scripts and then applied to the database in a controlled and repeatable way.

1. What is a migration?

Suppose you create a model:

Product
├── id
├── name
└── price

The database doesn't automatically know that you want a products table.

A migration is a script that describes the database schema change:

Python Model
     ↓
Migration Script
     ↓
Database Schema
2. Flask-SQLAlchemy + Alembic

In your task, you created:

class Product(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(100), nullable=False)
    price = db.Column(db.Float, nullable=False)

Flask-SQLAlchemy stores this schema information in:

db.metadata

You verified this with:

python -c "from Task3_Migrations import db; print(db.metadata.tables)"

and Alembic used that metadata to compare your Python models with the database.

The command you used:
alembic revision --autogenerate -m "create products table"

Alembic detected:

Detected added table 'products'

and generated:

63318ff55dbe_create_products_table.py

This is the migration script.

3. Applying the migration

You then ran:

alembic upgrade head

This told Alembic:

Apply all migrations until the latest migration.

Your output:

Running upgrade -> 63318ff55dbe, create products table

means the migration was successfully applied to the database.

4. Why not db.create_all()?

This is an important part of the task.

db.create_all() simply creates missing tables.

It doesn't give you a proper history of schema changes.

With Alembic:

Model Change
     ↓
Migration Script
     ↓
Migration History
     ↓
Database

For example, later you might add:

description = db.Column(db.String(255))

You can generate another migration:

alembic revision --autogenerate -m "add product description"

Then apply it:

alembic upgrade head

Now the database can be updated in a controlled way.

5. Django migrations

Django does essentially the same thing but provides its own migration system.

You change your model:

class Product(models.Model):
    name = models.CharField(max_length=100)
    price = models.FloatField()

Then:

python manage.py makemigrations

This generates the migration file.

Then:

python manage.py migrate

This applies the migration to the database.

So:

Django Model
     ↓
makemigrations
     ↓
Migration File
     ↓
migrate
     ↓
Database
6. Alembic vs Django
Flask + Alembic	Django
alembic revision --autogenerate	makemigrations
Generates migration	Generates migration
alembic upgrade head	migrate
Applies migration	Applies migration
Uses SQLAlchemy metadata	Uses Django model definitions
External migration tool	Built into Django
