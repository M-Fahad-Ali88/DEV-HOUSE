1. Inversion of Control (IoC)
IoC kya hai?

Inversion of Control ka simple matlab hai:

Application ke kisi component ka control khud component ke paas na ho, balkay koi framework/system us control ko manage kare.

Normal programming mein:

Application
    ↓
khud decide karti hai
    ↓
dependency kaise create karni hai

IoC mein:

Application
    ↓
Framework ko kehti hai:
"Mujhe ye dependency chahiye"
    ↓
Framework dependency provide karta hai
Simple example

Normal approach:

Route
  ↓
khud Database Connection banata hai
  ↓
Database use karta hai

Yahan Route ke paas control hai.

IoC approach:

Route
  ↓
"mujhe Database chahiye"
  ↓
Framework
  ↓
Database provide karta hai

Ab Route database creation ko control nahi karta.

IoC ka main purpose

IoC ka goal hai:

components ko loosely coupled banana
responsibilities separate karna
dependencies ko centrally manage karna
testing ko easier banana
resource lifecycle ko framework ke control mein dena
FastAPI mein IoC

FastAPI ka Dependency Injection system IoC ka practical example hai.

FastAPI kehta hai:

Tum sirf dependency declare karo.
Dependency ko create/resolve karna mera kaam hai.

Yahan se Depends() ka concept aata hai.

2. FastAPI Depends() Execution Tree

Depends() ko samajhne ka important point ye hai ke FastAPI dependencies ko tree ki form mein resolve karta hai.

Suppose:

Route
  ↓
get_user
  ↓
validate_token
  ↓
get_header

Iska matlab:

Route ko get_user chahiye
get_user ko token validation chahiye
token validation ko request header chahiye

Toh dependency structure:

             Route
               │
               ▼
           get_user
               │
               ▼
        validate_token
               │
               ▼
          get_header

Ye dependency execution tree hai.

FastAPI kya karta hai?

FastAPI pehle route ki dependencies ko identify karta hai.

Phir:

1. Dependency tree identify
          ↓
2. Lowest-level dependency resolve
          ↓
3. Result parent dependency ko
          ↓
4. Parent dependency resolve
          ↓
5. Finally route execute

Conceptually:

get_header()
    ↓
validate_token(header)
    ↓
get_user(token)
    ↓
route(user)

Yani route ko manually ye nahi karna:

header = get_header()
token = validate_token(header)
user = get_user(token)

FastAPI dependency graph ko resolve karta hai.

Tree kyun useful hai?

Suppose 10 routes ko authentication chahiye.

Instead of:

Route 1 → manually authentication
Route 2 → manually authentication
Route 3 → manually authentication
...

Dependency structure:

             Authentication
             /     |      \
            /      |       \
        Route1   Route2   Route3

Common dependency reusable ho jati hai.

3. Dynamic Resource Lifetimes

Ab third concept.

Resource lifetime ka matlab hai:

Koi resource kab create hota hai, kitni der available rehta hai, aur kab destroy/cleanup hota hai.

Examples:

Database Session
Database Connection
File
Network Connection
Temporary Object

Suppose ek HTTP request aati hai:

Request Start
     ↓
Database Session Create
     ↓
Route uses Database
     ↓
Request Complete
     ↓
Database Session Close

Is poore period ko resource ka lifetime keh sakte hain.

Dynamic kyun?

Resource lifetime fixed nahi hoti.

Different resources ka lifetime different ho sakta hai:

Application lifetime
        │
        ├── Configuration
        │
        └── Request
              │
              ├── DB Session
              ├── Authentication context
              └── Temporary resources

Kuch resources application ke saath start/end hote hain.

Kuch resources sirf ek request ke liye hote hain.

Important idea

Resource ko unnecessarily long time tak alive nahi rakhna chahiye.

For example:

Request starts
    ↓
DB session created
    ↓
Request finishes
    ↓
DB session should be released

Agar session unnecessarily application lifetime tak alive rahe, toh resource management problems aa sakti hain.

4. Scope Management

Scope ka matlab hai:

Dependency/resource kis boundary ke andar exist karega.

Tumhare current topic mein mainly do scopes important hain:

Request-level
Singleton
A. Request-Level Dependency

Request-level ka matlab:

Har request ka apna dependency instance/context ho.

Example:

Request 1
   ↓
DB Session 1

Request 2
   ↓
DB Session 2

Request 3
   ↓
DB Session 3

Diagram:

              Application
                   │
       ┌───────────┼───────────┐
       ↓           ↓           ↓
   Request 1   Request 2   Request 3
       ↓           ↓           ↓
    Session 1   Session 2   Session 3

Iska advantage:

requests isolated rehti hain
request-specific state safely maintain hoti hai
resources ko request ke end par release kiya ja sakta hai

Database sessions request-level resource ka common example hain.

5. Singleton Dependency

Singleton ka concept:

Puri application ke liye ek shared instance.

Diagram:

              Application
                   │
                   ▼
             One Instance
              /    |    \
             /     |     \
        Request1 Request2 Request3

Yani:

Request 1 ──┐
Request 2 ──┼──→ Same Instance
Request 3 ──┘

Example conceptual resources:

Application Configuration
Shared Settings
Certain stateless service objects
Singleton ka benefit

Agar koi object:

expensive to create ho
shared ho sakta ho
request-specific state na rakhta ho

toh usko repeatedly create karna unnecessary ho sakta hai.

6. Request-Level vs Singleton
Feature	Request-Level	Singleton
Instance	Har request	Ek shared instance
Lifetime	Request tak	Application tak
State	Request-specific	Shared
Isolation	High	Low/shared
Typical use	DB session	Configuration/service
Creation	Multiple	Usually once

Simple rule:

Request-specific resource
        ↓
Request-level

Aur:

Application-wide shared resource
        ↓
Singleton
7. In Chaar Concepts Ka Connection

Ye chaar separate topics nahi hain. Ye ek doosre se connected hain:

                IoC
                 ↓
        Framework controls
                 ↓
          Dependencies
                 ↓
             Depends()
                 ↓
       Dependency Execution Tree
                 ↓
       Dependency Resolution
                 ↓
       Resource Creation/Lifetime
                 ↓
          Scope Management
           ↙             ↘
   Request-level       Singleton
Ek sentence mein poora concept:

IoC control framework ko deta hai, Depends() dependencies ko declare aur resolve karne ka mechanism deta hai, resource lifetime decide karta hai resource kab create/use/cleanup hoga, aur scope management decide karta hai ke resource har request ke liye hoga ya application-wide shared hoga.
