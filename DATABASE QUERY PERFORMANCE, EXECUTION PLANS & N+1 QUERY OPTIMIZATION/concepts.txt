DATABASE QUERY PERFORMANCE — THEORETICAL FOCUS
1. Database Query Performance

Database query performance refers to how efficiently a database processes a query and returns the required data.

The main performance factors are:

Execution time — how long the query takes.
Query count — number of queries sent to the database.
Rows scanned — number of rows the database examines.
Rows returned — number of rows returned to the application.
CPU and memory usage — resources required to process the query.
Disk I/O — amount of data read from storage.
Network latency — time required for communication between application and database.
Example
Efficient:
Application → Database → Result

Inefficient:
Application → Database → Result
Application → Database → Result
Application → Database → Result
...

A query that runs quickly once can still cause a performance problem if the application executes it thousands of times.

2. Execution Plans

An execution plan is the strategy chosen by the database to execute a SQL query.

When you send:

SELECT *
FROM products
WHERE category_id = 5;

the database optimizer determines how to find those rows.

Conceptually:

SQL Query
    ↓
Parser
    ↓
Query Optimizer
    ↓
Execution Plan
    ↓
Database Operations
    ↓
Result

An execution plan can show operations such as:

Table/Sequential Scan
Index Scan
Index Lookup
Joins
Sorting
Filtering
Estimated rows
Actual rows
Cost of operations
EXPLAIN

Most relational databases provide an EXPLAIN command:

EXPLAIN
SELECT *
FROM products
WHERE category_id = 5;

Some databases also provide:

EXPLAIN ANALYZE
SELECT *
FROM products
WHERE category_id = 5;

EXPLAIN helps you understand how the database plans to execute the query, while EXPLAIN ANALYZE can provide actual execution information when supported.

3. Database Indexes

An index is a database data structure designed to make finding rows more efficient.

Without an index:

Table
 ↓
Check many/all rows
 ↓
Find matching row

With an appropriate index:

Index
 ↓
Find matching value
 ↓
Locate required row

For example:

CREATE INDEX idx_products_category
ON products(category_id);

Now queries filtering by category_id may be able to use that index.

Advantages
Faster data retrieval
Faster filtering
Can improve joins
Can improve certain sorting operations
Disadvantages
Requires additional storage
Indexes need maintenance
Can make INSERT, UPDATE, and DELETE more expensive

Therefore, indexes should be created based on actual query patterns rather than adding them to every column.

4. Avoiding Unnecessary Database Round-Trips

A database round-trip occurs when the application communicates with the database and receives a response.

For example:

Application
    ↓
SQL Query
    ↓
Database
    ↓
Result
    ↓
Application

Every unnecessary round-trip adds overhead.

Suppose you retrieve 1,000 products:

1 query → Get products
1000 queries → Get each product's category

Total = 1001 queries

Even if each individual query is fast, repeatedly communicating with the database can significantly increase overall execution time.

The goal is to retrieve the required data efficiently while avoiding unnecessary requests.

5. N+1 Query Problem

The N+1 query problem is a common example of unnecessary database round-trips.

It occurs when:

1 query → Retrieve N records
N queries → Retrieve related data individually

Therefore:

Total queries = N + 1

For 1,000 records:

1 + 1000 = 1001 queries

Instead of repeatedly requesting related data, applications can use techniques such as:

Django:
select_related()
prefetch_related()

SQLAlchemy:
joinedload()
subqueryload()

These are forms of eager loading that allow related data to be loaded more efficiently.

Yes. In SQLAlchemy, the same N+1 problem can happen.

Suppose we have:

Product
   ↓
Category

Each product belongs to one category.

❌ N+1 problem in SQLAlchemy
products = session.query(Product).all()

This executes:

1 query → Get 1,000 products

Then:

for product in products:
    print(product.category.name)

If category is lazily loaded, SQLAlchemy may execute an additional query for each product:

1 query  → Get 1,000 products

1 query  → Category for Product 1
1 query  → Category for Product 2
1 query  → Category for Product 3
...
1 query  → Category for Product 1000

Therefore:

1 + 1000 = 1001 queries

That's the N+1 query problem.

✅ Fix with joinedload()

SQLAlchemy provides joinedload() for eager loading:

from sqlalchemy.orm import joinedload

products = (
    session.query(Product)
    .options(joinedload(Product.category))
    .all()
)

for product in products:
    print(product.category.name)

Now SQLAlchemy loads the products and their categories using an eager-loading strategy based on a JOIN.

Conceptually:

Without joinedload:

Query 1 → 1,000 Products
Query 2 → Category 1
Query 3 → Category 2
...
Query 1001 → Category 1000


With joinedload():

Query → Products + Categories

So instead of 1,001 unnecessary queries, you avoid the per-product category queries.

subqueryload()

SQLAlchemy also provides:

from sqlalchemy.orm import subqueryload

products = (
    session.query(Product)
    .options(subqueryload(Product.category))
    .all()
)

This uses a separate eager-loading query rather than loading the relationship through the same JOIN.

Easy comparison
Django
────────────────────────
select_related()    → JOIN-style eager loading
prefetch_related()  → Separate query eager loading


SQLAlchemy
────────────────────────
joinedload()        → JOIN-style eager loading
subqueryload()      → Separate query eager loading

Yes, your idea is basically correct, but one small correction:

An index is not exactly an address that we give the database. It's more like a separate lookup structure that helps the database quickly find rows based on a particular column.

Simple example

Suppose your table is:

PRODUCTS
--------------------------------
id | product_name | price
--------------------------------
1  | Laptop       | 1000
2  | Mouse        | 20
3  | Keyboard     | 50
...

You create an index on product_name:

CREATE INDEX idx_product_name
ON products(product_name);

Now when you run:

SELECT *
FROM products
WHERE product_name = 'Laptop';

The database can use the product_name index to quickly locate the matching row instead of potentially checking every row in the table.

Think of it like a book 📖

Without an index:

Database
   ↓
Check row 1
Check row 2
Check row 3
...
Check many rows
   ↓
Find "Laptop"

With an index:

Product Name Index
       ↓
"Laptop" → location/reference to matching row
       ↓
PRODUCTS table
       ↓
Get the row
One important point

The index doesn't mean the database only searches the product_name column and ignores the rest of the table.

Rather:

It uses product_name to quickly locate the relevant row, then retrieves the other required columns from that row.

For example:

SELECT product_name, price
FROM products
WHERE product_name = 'Laptop';

The index helps find which row(s) match "Laptop", and then the database gets the price and other requested data.

So your mental model can be:

Index = a fast lookup system for a column → helps database find relevant rows quickly. ✅

Final Concepts — Eager Loading

We used 4 eager-loading techniques in today's tasks:

Django ORM
├── select_related()
└── prefetch_related()

SQLAlchemy
├── joinedload()
└── subqueryload()
1. Django — select_related()

Used for: ForeignKey and OneToOneField

It uses a SQL JOIN to retrieve related objects in the same query.

Our example:

InventoryItem
      ↓ ForeignKey
Product
      ↓ ForeignKey
Category

Without eager loading:

InventoryItem query
       ↓
Product query
       ↓
Category query

With:

InventoryItem.objects.select_related("product__category")

Django uses JOINs and can retrieve everything in 1 query.

InventoryItem + Product + Category
              ↓
          1 query

Remember:

select_related() = JOIN = best suited for single-valued relationships.

2. Django — prefetch_related()

Used for: Many-to-Many and reverse relationships, and it can also be used for ForeignKeys.

Instead of using one large JOIN, Django performs separate queries and combines the results in Python.

Example:

InventoryItem.objects.prefetch_related(
    "product__category"
)

Our result:

Query 1 → InventoryItems
Query 2 → Products
Query 3 → Categories

So:

3 queries

instead of:

2,001 queries

Remember:

prefetch_related() = separate queries + Python combination = useful for collections/multiple related objects.

3. SQLAlchemy — joinedload()

Used for: Eager loading through SQL JOIN.

Example:

session.query(InventoryItem).options(
    joinedload(
        InventoryItem.product
    ).joinedload(
        Product.category
    )
).all()

SQLAlchemy retrieves:

InventoryItem
      ↓ JOIN
Product
      ↓ JOIN
Category

Our result:

1 query

Remember:

joinedload() = SQL JOIN-based eager loading.

It is particularly useful when loading single related objects, such as:

Product → Category
4. SQLAlchemy — subqueryload()

Used for: Eager loading through separate queries.

Example:

session.query(InventoryItem).options(
    subqueryload(
        InventoryItem.product
    ).subqueryload(
        Product.category
    )
).all()

Instead of joining everything together, SQLAlchemy performs separate queries.

Our result:

Query 1 → InventoryItems
Query 2 → Products
Query 3 → Categories

Therefore:

3 queries

Remember:

subqueryload() = separate-query eager loading, useful especially when loading collections.
