Theoretical Focus:

1. Client-Side JavaScript Execution

Modern websites mein aksar sara data initial HTML response mein nahi hota. Iske bajaye JavaScript browser ke andar execute hoti hai, APIs ke saath communicate karti hai, received data ko process karti hai, aur webpage ko update karti hai.

Playwright humein ek real browser ko control karne deta hai, jiski wajah se website ki JavaScript normally execute hoti hai.

2. Dynamic DOM Mutations

JavaScript page load hone ke baad bhi DOM ko continuously modify kar sakti hai. Ismein elements ko add karna, remove karna, ya existing elements ko change karna shamil hai.

Ismein:

dynamically generated content
infinite scrolling
JavaScript-rendered tables

shamil hain.

Playwright updated DOM ke saath interact kar sakta hai jab JavaScript usmein changes kar chuki ho.

3. Shadow DOM

Modern web applications aksar Web Components use karti hain jinmein Shadow DOM hota hai. Shadow DOM component ke internal structure ko normal document structure se separate rakhta hai.

Traditional scraping techniques ko Shadow DOM ke elements access karne mein difficulty ho sakti hai. Playwright browser-level locators provide karta hai jinki madad se in components ke saath interact kiya ja sakta hai.

4. Network Traffic Interception

Dynamic webpages aksar apna data XHR, Fetch aur WebSocket connections ke through receive karti hain.

Rendered HTML se sirf data extract karne ke bajaye, Playwright browser ki network activity ko monitor karke underlying responses ya messages ko capture kar sakta hai.

Iska matlab hai ke hum data ko us stage par capture kar sakte hain jab website usay browser mein render karne se pehle network se receive karti hai.

5. Browser Automation with Playwright

Playwright Chromium, Firefox aur WebKit ko automatically control kar sakta hai.

Iski madad se hum:

webpage navigation
scrolling
clicking
dynamic content ka wait
web components ke saath interaction
network traffic monitoring

jaise tasks perform kar sakte hain.

Overall Concept

Ye topic static HTML scraping se modern JavaScript-driven applications ki scraping ki taraf move karta hai.

Ismein humein do cheezon ko samajhna important hai:

Browser ke andar JavaScript ki wajah se change hone wala DOM aur website ke backend ke saath hone wali underlying network communication.


Playwright ek browser automation framework/library hai jo programmatically web browsers ko control karne ke liye use hota hai.

Playwright ke through hum Python code se browser ko control kar sakte hain, bilkul aise jaise koi real user browser use kar raha ho.

Task 2 — Network Traffic Interception

Task 2 ka main idea yeh hai ke modern website par data sirf HTML mein nahi hota. JavaScript background mein server se data mangwati hai.

Playwright ki help se hum browser ke andar hone wali network communication ko directly observe/intercept kar sakte hain.

Is Task 2 ke do parts hain:

XHR / Fetch Interception
WebSocket Interception
Part 1 — XHR / Fetch Interception
Basic concept

Jab webpage JavaScript ke through server/API se data request karti hai, commonly:

Browser
   ↓
JavaScript
   ↓
Fetch / XHR Request
   ↓
Server / API
   ↓
JSON Response
   ↓
JavaScript
   ↓
DOM

For example, webpage JavaScript ye request kar sakti hai:

fetch("/api/products")

Server response deta hai:

{
    "products": [
        {
            "id": 1,
            "name": "Laptop",
            "price": 120000
        }
    ]
}

Normally browser is JSON ko receive karta hai aur JavaScript usko webpage ke HTML/DOM mein display kar deti hai.

Humne kya kiya?

Playwright ne browser ki response event ko listen kiya:

page.on("response", handle_response)

Iska matlab:

"Jab browser ko koi response mile, mujhe batao."

Phir humne response ka URL aur status dekha:

print(response.url)
print(response.status)

Aur JSON response ko directly read kiya:

data = await response.json()

Is tarah hum DOM se data scrape karne ke bajaye API response se directly data obtain kar sakte hain.

Hamare example mein

JavaScript:

fetch("/api/products")

ne API request bheji.

Playwright ne us response ko intercept kiya:

API Response Detected
URL: http://demo.local/api/products
Status: 200

Phir raw payload mila:

{
    "products": [
        {
            "id": 1,
            "name": "Laptop",
            "price": 120000
        },
        {
            "id": 2,
            "name": "Keyboard",
            "price": 5000
        },
        {
            "id": 3,
            "name": "Mouse",
            "price": 2500
        }
    ]
}

Uske baad JavaScript ne isi data ko DOM mein render kiya:

Laptop - 120000
Keyboard - 5000
Mouse - 2500

Yahan important point:

Humne data ko DOM mein render hone se pehle network response se dekh liya.

Conceptually:

              ┌──→ Playwright intercepts
              │
JavaScript → Fetch → API → JSON
                         │
                         ↓
                    JavaScript
                         │
                         ↓
                        DOM

Isliye Task 2 Part 1 ka focus hai:

API se aane wale raw HTTP response ko browser network level par capture karna.

Part 2 — WebSocket Interception

WebSocket thoda different hai.

Fetch/XHR usually:

Request → Response

hota hai.

WebSocket ek persistent connection establish karta hai:

Browser ←→ WebSocket Server

Connection continuously open reh sakta hai aur dono sides messages send/receive kar sakti hain.

For example:

Browser
   │
   │ WebSocket connection
   │
   ▼
Server

Connection establish hone ke baad:

Browser ───────→ Server
       Message 1

Browser ←─────── Server
       Message 2

Browser ───────→ Server
       Message 3

Browser ←─────── Server
       Message 4

Ye real-time applications mein useful hota hai, jaise:

live chat
real-time notifications
live dashboards
multiplayer games
live updates
Playwright WebSocket ko kaise intercept karta hai?

Playwright mein humne use kiya:

page.on("websocket", handle_websocket)

Iska matlab:

"Jab page koi WebSocket connection create kare, mujhe notify karo."

Phir:

ws.on("framesent", ...)

se hum browser se server ko bheje jaane wale messages capture karte hain.

Aur:

ws.on("framereceived", ...)

se server se browser ko aane wale messages capture karte hain.

Hamare example mein

Browser ne connection establish kiya:

WebSocket Connected
URL: ws://127.0.0.1:8765/

Phir browser ne ye JSON send kiya:

{
    "type": "message",
    "user": "Fahad",
    "text": "Hello WebSocket"
}

Playwright ne ise capture kiya:

Sent: {"type":"message","user":"Fahad","text":"Hello WebSocket"}

Server ne message receive kiya:

Server Received:
{"type":"message","user":"Fahad","text":"Hello WebSocket"}

Server ne response bheja.

Playwright ne received frame capture kiya:

Received:
{
    "status": "success",
    "message": "WebSocket payload received",
    "data": ...
}

So complete flow:

Browser
   │
   │ Sent frame
   ▼
WebSocket Server
   │
   │ Received frame
   │
   │ Response
   ▼
Browser
   │
   ▼
Playwright intercepts
Part 1 vs Part 2 — Main Difference

Sabse important difference ye hai:

XHR / Fetch
Request
   ↓
Response
   ↓
Done

Ye generally individual HTTP requests ke liye hota hai.

WebSocket
Connection
   ↕
Continuous messages
   ↕
Connection remains open

Isliye WebSocket mein hum frames/messages monitor karte hain, jabke Fetch/XHR mein hum HTTP responses monitor karte hain.

Ek simple real-world example

Suppose ek website par live stock price hai.

Agar website:

Fetch API

use karti hai:

Browser → GET /api/stock → Server
Browser ← JSON price ← Server

Hum Fetch response intercept karenge.

Lekin agar website continuously price updates WebSocket se bhejti hai:

Browser ←→ WebSocket Server

$245.20
$245.35
$245.18
$245.42
...

to hum WebSocket frames intercept karenge.
