1. WSGI — WEB SERVER GATEWAY INTERFACE

WSGI is a standard interface between a Python web server and a Python web application.

The important thing is that WSGI is a specification, not a web server.

BASIC ARCHITECTURE
CLIENT
   ↓
WEB SERVER
   ↓
WSGI SERVER
   ↓
WSGI APPLICATION
   ↓
YOUR PYTHON CODE
   ↓
RESPONSE

For example:

Browser
   ↓
Gunicorn
   ↓
Flask/Django
   ↓
Your Python application
WHY WSGI WAS CREATED

Before WSGI, Python web frameworks and web servers didn't have one standardized way to communicate.

WSGI established a common interface:

WEB SERVER  ←→  WSGI  ←→  WEB APPLICATION

This meant a framework such as Flask could work with different WSGI servers without needing a completely different integration for each server.

HOW WSGI EXECUTES A REQUEST

A simplified WSGI application looks like:

def application(environ, start_response):
    start_response(
        "200 OK",
        [("Content-Type", "text/plain")]
    )

    return [b"Hello World"]

There are two important arguments:

environ

Contains information about the HTTP request.

For example:

HTTP_METHOD
PATH_INFO
QUERY_STRING
CONTENT_TYPE
SERVER_NAME
SERVER_PORT

Conceptually:

HTTP Request
     ↓
   environ
     ↓
WSGI application
start_response

The application uses this to provide the HTTP status and headers.

start_response(
    "200 OK",
    [("Content-Type", "text/plain")]
)

Then the application returns the response body:

return [b"Hello World"]
THE IMPORTANT PART: SYNCHRONOUS EXECUTION

WSGI follows a synchronous execution model.

Suppose you have:

def get_data():
    data = database_query()
    return data

If the database takes 500 ms:

REQUEST
   ↓
DATABASE QUERY
   ↓
WAIT 500ms
   ↓
RETURN DATA
   ↓
RESPONSE

The worker handling that request is occupied during that operation.

This is one of the major limitations that ASGI was designed to address.

MULTIPLE WSGI REQUESTS

Suppose Gunicorn has 3 worker processes:

Gunicorn
│
├── Worker 1 → Request A
├── Worker 2 → Request B
└── Worker 3 → Request C

If all three workers are busy:

Worker 1 → Request A → waiting for database
Worker 2 → Request B → processing
Worker 3 → Request C → waiting for API

Request D → WAITING

Adding more workers can increase concurrency, but each worker is still executing synchronously.

WSGI VS ASGI — THE CORE DIFFERENCE

The simplest mental model is:

WSGI
────
Synchronous
    ↓
Request
    ↓
Execute
    ↓
Wait
    ↓
Response

Whereas:

ASGI
────
Asynchronous
    ↓
Request
    ↓
Coroutine
    ↓
await I/O
    ↓
Event loop handles other work
    ↓
Resume coroutine
    ↓
Response

This distinction is extremely important for understanding FastAPI and Uvicorn.

WHAT YOU SHOULD REMEMBER
WSGI

Web Server Gateway Interface

Standard interface
Python web applications
Synchronous-first
Traditionally HTTP request/response
Used by Flask and traditional Django deployments
Commonly served through Gunicorn/uWSGI
Key mental model

WSGI provides a standardized synchronous interface between a web server and Python application.



2. ASGI — ASYNCHRONOUS SERVER GATEWAY INTERFACE

ASGI is the modern Python standard for connecting web servers with asynchronous Python applications.

It was designed as an evolution of WSGI.

BASIC ARCHITECTURE
CLIENT
   ↓
ASGI SERVER
   ↓
ASGI APPLICATION
   ↓
FASTAPI / STARLETTE
   ↓
YOUR CODE

A common example:

Browser
   ↓
Uvicorn
   ↓
FastAPI
   ↓
Your endpoint
WHY ASGI WAS CREATED

WSGI works well for traditional synchronous HTTP applications, but modern applications need things like:

Asynchronous I/O
WebSockets
Long-lived connections
Streaming
Large numbers of concurrent connections
Real-time communication

ASGI provides an interface designed to support these use cases.

ASGI APPLICATION

A simplified ASGI application looks like this:

async def application(scope, receive, send):
    ...

There are three important concepts here:

1. scope

Contains information about the connection/request.

For example:

scope
 ├── type
 ├── method
 ├── path
 ├── headers
 └── query_string

For an HTTP request:

type = "http"
method = "GET"
path = "/users"
2. receive

Used to receive events/messages from the client.

Conceptually:

CLIENT
   ↓
receive()
   ↓
ASGI APPLICATION
3. send

Used to send events/messages back to the client.

ASGI APPLICATION
   ↓
send()
   ↓
CLIENT
ASGI IS EVENT-BASED

This is one of the most important differences from WSGI.

Instead of thinking:

REQUEST → FUNCTION → RESPONSE

ASGI can be thought of as:

CONNECTION
    ↓
EVENTS
    ↓
APPLICATION
    ↓
EVENTS
    ↓
CLIENT

For HTTP, you can have events such as:

http.request
http.response.start
http.response.body

This event-based design also makes protocols such as WebSockets possible.

ASYNC AND AWAIT

This is where ASGI becomes particularly powerful.

Consider:

async def get_user():
    user = await database_query()
    return user

The important keyword is:

await

When the coroutine reaches an operation that can wait asynchronously:

Request
   ↓
get_user()
   ↓
await database_query()
   ↓
Coroutine pauses
   ↓
Event loop handles other work
   ↓
Database response arrives
   ↓
Coroutine resumes
   ↓
Response

The event loop doesn't need to sit there doing nothing while the I/O operation is pending.

MULTIPLE REQUESTS

Imagine three requests:

Request A → database → await
Request B → API       → await
Request C → database → await

The event loop can coordinate them:

              EVENT LOOP
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
   Coroutine A  Coroutine B  Coroutine C
        │         │         │
      await     await      await
        │         │         │
        └─────────┼─────────┘
                  ↓
          Resume when ready

This is concurrency, not necessarily parallel CPU execution.

That's an important distinction.

ASGI DOES NOT AUTOMATICALLY MAKE EVERYTHING FASTER

This is a common misconception.

Consider:

async def endpoint():
    result = cpu_heavy_function()
    return result

If cpu_heavy_function() takes 5 seconds and blocks the event loop, other coroutines may be prevented from making progress on that event-loop thread.

ASGI is especially beneficial for I/O-bound workloads when the underlying operations support asynchronous execution.

For CPU-heavy work, you may need processes, threads, worker pools, or other architecture.

WSGI VS ASGI
Feature	WSGI	ASGI
Execution model	Synchronous-first	Async-capable
Interface	Callable	Event-based async callable
async/await	Not native	Native
WebSockets	Not designed for it	Supported
Long-lived connections	Limited	Designed for it
Async I/O	Limited	Excellent fit
FastAPI	❌	✅
Flask	✅	Can have ASGI-related deployment options, but WSGI remains central
Django	WSGI/ASGI	Both
THE BIG PICTURE

You should now have this mental model:

WSGI
 │
 ├── Synchronous
 ├── Request/Response
 └── Traditional Python web applications


ASGI
 │
 ├── Async-capable
 ├── Event-based
 ├── async/await
 ├── WebSockets
 └── Modern asynchronous applications

And for your project:

CLIENT
   ↓
UVICORN
   ↓
ASGI
   ↓
FASTAPI
   ↓
YOUR ENDPOINT
   ↓
ASYNCIO EVENT LOOP
   ↓
ASYNC I/O
The key sentence to remember

ASGI is an asynchronous, event-based interface that allows Python web applications to handle HTTP and other protocols using asynchronous execution.



3. UVICORN / GUNICORN PROCESS MANAGEMENT

Now we move from ASGI itself to the servers that actually run your ASGI application.

The most important thing to understand is:

Uvicorn runs the ASGI application, while Gunicorn manages multiple worker processes.

1. WHAT IS UVICORN?

Uvicorn is an ASGI web server.

Its job is to:

Receive HTTP Request
        ↓
Uvicorn
        ↓
ASGI Interface
        ↓
FastAPI
        ↓
Response
        ↓
Uvicorn
        ↓
Client

For example:

uvicorn main:app

This means:

main.py
   ↓
app
   ↓
Uvicorn

If your main.py contains:

from fastapi import FastAPI

app = FastAPI()

then:

uvicorn main:app

tells Uvicorn:

main → Python module
app → ASGI application object
2. WHAT DOES UVICORN ACTUALLY DO?

Uvicorn handles several important responsibilities:

NETWORKING

It listens for incoming connections:

CLIENT
   ↓
TCP CONNECTION
   ↓
UVICORN
HTTP PROCESSING

It receives HTTP messages and translates them into ASGI events.

HTTP REQUEST
     ↓
UVICORN
     ↓
ASGI EVENTS
     ↓
FASTAPI
EVENT LOOP

Uvicorn runs an asynchronous event loop, typically through Python's asyncio ecosystem.

Conceptually:

Uvicorn Process
      ↓
Event Loop
      ↓
┌─────┼─────┐
↓     ↓     ↓
Task A Task B Task C

This allows asynchronous requests to be coordinated concurrently.

3. WHAT IS GUNICORN?

Gunicorn is primarily a process manager and application server.

Its major strength is managing multiple worker processes.

For example:

gunicorn main:app -w 4

Conceptually:

Gunicorn Master
      │
 ┌────┼────┬────┐
 ↓    ↓    ↓    ↓
W1   W2   W3   W4

Each worker is a separate operating-system process.

4. WHY USE MULTIPLE PROCESSES?

Suppose you have:

CPU
├── Core 1
├── Core 2
├── Core 3
└── Core 4

You can run multiple worker processes:

Worker 1 → Process
Worker 2 → Process
Worker 3 → Process
Worker 4 → Process

Processes have their own memory space.

This is important because multiple processes can provide:

Better CPU utilization
Isolation
Greater resilience
Parallel execution across CPU cores
5. UVICORN VS GUNICORN

This is the part you should remember carefully.

Uvicorn	Gunicorn
ASGI server	Process manager/application server
Handles ASGI	Manages workers
Handles networking	Manages processes
Runs event loop	Creates/manages worker processes
Great for async applications	Great for production worker management

Think:

UVICORN
   ↓
"HOW DO I RUN THE ASGI APPLICATION?"

while:

GUNICORN
   ↓
"HOW MANY WORKERS SHOULD RUN?"
"HOW SHOULD I MANAGE THEM?"
6. USING THEM TOGETHER

For an ASGI application, a common architecture is:

                    GUNICORN
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
      Worker 1      Worker 2      Worker 3
          │            │            │
       Uvicorn      Uvicorn      Uvicorn
          │            │            │
       Event Loop   Event Loop   Event Loop
          │            │            │
       FastAPI      FastAPI      FastAPI

For example:

gunicorn main:app -w 4 -k uvicorn.workers.UvicornWorker

Break it down:

gunicorn
    ↓
Start Gunicorn

main:app
    ↓
Load the FastAPI application

-w 4
    ↓
Create 4 workers

-k uvicorn.workers.UvicornWorker
    ↓
Use Uvicorn-based workers
    ↓
Run the application as ASGI
7. PROCESS VS THREAD VS COROUTINE

This distinction is very important for your theoretical focus.

PROCESS

An operating-system process has its own memory space.

Process 1
└── Memory

Process 2
└── Memory

Gunicorn workers are typically separate processes.

THREAD

Threads exist inside a process.

Process
│
├── Thread 1
├── Thread 2
└── Thread 3

Threads share the process's memory.

COROUTINE

A coroutine is an asynchronous unit of execution.

Event Loop
│
├── Coroutine A
├── Coroutine B
└── Coroutine C

Coroutines are much lighter than processes and threads.

8. PUTTING EVERYTHING TOGETHER

This is the architecture you should visualize:

                         CLIENTS
                            │
                            ↓
                      GUNICORN
                  Process Manager
                            │
             ┌──────────────┼──────────────┐
             ↓              ↓              ↓
         PROCESS 1      PROCESS 2      PROCESS 3
             │              │              │
          Uvicorn        Uvicorn        Uvicorn
             │              │              │
         Event Loop     Event Loop     Event Loop
             │              │              │
       ┌─────┼─────┐  ┌─────┼─────┐  ┌─────┼─────┐
       ↓     ↓     ↓  ↓     ↓     ↓  ↓     ↓     ↓
      C1    C2    C3 C4    C5    C6 C7    C8    C9

Where:

C = Coroutine

So one Uvicorn worker can manage multiple asynchronous tasks/coroutines, while Gunicorn can manage multiple worker processes.

9. WHY MULTIPLE UVICORN WORKERS?

Suppose you run:

uvicorn main:app --workers 4

You can conceptually think of it as:

Main Process
     │
 ┌───┼───┬───┐
 ↓   ↓   ↓   ↓
 W1  W2  W3  W4
 │   │   │   │
 ↓   ↓   ↓   ↓
EL  EL  EL  EL

Each worker has its own event loop.

So:

Worker 1 → Event Loop 1
Worker 2 → Event Loop 2
Worker 3 → Event Loop 3
Worker 4 → Event Loop 4

This gives you multiple processes + asynchronous concurrency inside each process.

10. THE CRITICAL CONCEPT

Don't think:

"ASGI means multiple processes."

That's incorrect.

Instead:

ASGI
 ↓
Application interface supporting async execution


Uvicorn
 ↓
ASGI server + event loop


Gunicorn
 ↓
Worker/process management


Coroutine
 ↓
Unit of asynchronous execution

These are different layers.

COROUTINE-BASED REQUEST HANDLING — SHORT VERSION
A coroutine is created using async def.
await allows a coroutine to pause while waiting for an asynchronous operation.
During this pause, the event loop can handle other requests.
When the operation finishes, the coroutine resumes.
This enables efficient handling of many I/O-bound concurrent requests.
Blocking operations like time.sleep() or heavy CPU tasks can block the event loop.

REQUEST
   ↓
ASYNC ENDPOINT
   ↓

   ↓

   ↓
COROUTINE PAUSES
   ↓
EVENT LOOP HANDLES OTHER REQUESTS
   ↓
OPERATION COMPLETES
   ↓
COROUTINE RESUMES
   ↓
RESPONSE


PYDANTIC V2 SCHEMA COMPILATION MECHANICS — SHORT VERSION
Pydantic uses Python type hints to define and validate data.
BaseModel creates a structured schema from your field definitions.
Pydantic v2 uses pydantic-core, implemented in Rust, for fast validation.
The schema is prepared/compiled into efficient validation logic.
Input data is validated and, when allowed, automatically coerced to the required type.
Field constraints such as min_length, gt, and le are enforced.
Custom validation logic can be added using validators.
FLOW
REQUEST DATA
    ↓
PYDANTIC MODEL
    ↓
CORE SCHEMA
    ↓
PYDANTIC-CORE VALIDATION
    ↓
TYPE COERCION + CONSTRAINT CHECKS
    ↓
CUSTOM VALIDATORS
    ↓
VALIDATED PYTHON OBJECT
EXAMPLE
from pydantic import BaseModel, Field

class User(BaseModel):
    name: str = Field(min_length=3)
    age: int = Field(gt=0)

Key idea: Pydantic v2 converts your type definitions into an efficient validation schema, which is then used to validate incoming data quickly.
